# Перехід гри Squares на багатокористувацький режим (Multiplayer) за допомогою Supabase

Цей документ містить архітектурний план та результати брейнштормінгу щодо перетворення локальної гри **Squares (Territory capture duel)** на багатокористувацьку онлайн-гру. 

Ми пропонуємо використовувати **Supabase** як бекенд-платформу завдяки вбудованій підтримці бази даних PostgreSQL, механізму аутентифікації та функціям реального часу (Realtime Broadcast/Presence/Database Changes).

> [!NOTE]
> **Поточний статус (12.07.2026):**
> 1. Створено проект Supabase `SquaresGame` у регіоні `eu-central-1` (дані записано в `supabase_info.md`).
> 2. **Зупинилися на:** виборі платформи для хостингу сайту та налаштуванні GitHub-репозиторію.
> 3. **Наступний крок при поверненні:** ініціалізація локального репозиторію `git init`, створення репозиторію на GitHub користувачем, зв'язування їх та пуш коду, після чого почнемо налаштування таблиць в Supabase та розбиття коду на Vite-модулі.

## 💾 Схема бази даних (Database Schema)

Для роботи мультиплеєра нам знадобляться такі таблиці в Supabase:

### 1. `rooms` (Ігрові кімнати)
Зберігає налаштування гри та загальний статус.
* `id` (uuid, PK) — унікальний ідентифікатор.
* `code` (varchar) — короткий код кімнати (наприклад, `XF4G8A`) для зручного підключення.
* `host_id` (uuid) — ідентифікатор користувача-створювача (хоста).
* `grid_size` (integer) — розмір сітки (15, 20, 30).
* `map_type` (varchar) — тип карти ("classic", "asteroids" тощо).
* `players_count` (integer) — ліміт гравців (2-6).
* `enable_advanced_rules` (boolean) — чи увімкнені розширені правила (дублі).
* `enable_team_mode` (boolean) — командний режим.
* `status` (varchar) — статус кімнати (`"waiting"`, `"playing"`, `"finished"`).
* `created_at` (timestamp) — час створення.

### 2. `game_states` (Стан активної гри)
Оскільки Squares є покроковою грою, збереження всього стану (включаючи поле 2D) в БД гарантує стійкість до оновлень сторінки чи дисконектів.
* `room_id` (uuid, PK, References `rooms.id` ON DELETE CASCADE).
* `board` (jsonb) — 2D-масив розміру $N\times N$, що відображає ігрове поле.
* `active_player` (integer) — індекс гравця, чий зараз хід (1-6).
* `current_roll` (integer[]) — значення кубиків (наприклад, `[3, 5]`).
* `has_rolled` (boolean) — чи кинув гравець кубики в цьому ходу.
* `consecutive_passes` (integer) — кількість послідовних пасів.
* `double_size_multiplier` (jsonb) — множники для наступного ходу (для розширених правил).
* `consecutive_skipped_turns` (jsonb) — лічильники пропусків для камбеку.
* `active_special_move` (varchar) — статус спеціальних ходів (наприклад, режим малювання стіни).
* `custom_cells_to_place` (integer) — кількість клітин для малювання.
* `custom_cells_placed` (jsonb) — координати вже намальованих клітин.
* `is_game_over` (boolean) — чи завершено гру.
* `winner_index` (integer) — індекс переможця.
* `updated_at` (timestamp) — час останньої дії.

### 3. `players` (Учасники кімнати)
Зв'язок реальних підключених гравців зі слотами у грі (Player 1, Player 2 тощо).
* `id` (uuid, PK) — ідентифікатор користувача (зв'язаний з `auth.users.id`).
* `room_id` (uuid, References `rooms.id` ON DELETE CASCADE).
* `player_index` (integer) — номер гравця в грі (1-6).
* `name` (varchar) — відображуване ім'я.
* `color` (varchar) — обраний колір (cyan, pink, emerald...).
* `team` (integer) — команда (якщо командний режим).
* `is_ready` (boolean) — статус готовності у лобі.
* `joined_at` (timestamp) — час приєднання.

### 4. `profiles` (Постійні профілі користувачів)
Зберігає тривалу статистику для таблиці лідерів та персоналізації.
* `id` (uuid, PK, References `auth.users.id` ON DELETE CASCADE).
* `username` (varchar) — ім'я користувача (за замовчуванням береться з Google).
* `avatar_url` (varchar) — посилання на аватар користувача з Google.
* `games_played` (integer, default 0) — зіграно ігор всього.
* `games_won` (integer, default 0) — виграно ігор.
* `total_cells_captured` (integer, default 0) — загальна площа захопленої території.
* `created_at` (timestamp) — дата створення акаунту.

> [!TIP]
> При першій авторизації гравця через Google Auth, за допомогою PostgreSQL Trigger ми будемо автоматично створювати запис у таблиці `profiles`, витягуючи `display_name` та `avatar_url` з метаданих Google-акаунту. Після завершення гри, результати автоматично оновлюватимуть статистику перемог та захоплених клітинок.

## 🔄 Ігровий процес у режимі Реального Часу (Realtime Sync)

Ми поєднаємо два підходи в Supabase Realtime:
1. **Postgres Changes (Підписка на зміни в БД):**
   * Клієнти підписуються на оновлення рядка у `game_states` для своєї кімнати.
   * Коли гравець робить хід (кидає кубики, ставить фігуру, пасує), він викликає функцію оновлення `game_states` у БД.
   * Supabase миттєво розсилає зміни всім гравцям. Клієнти оновлюють свій локальний `state` і перемальовують Canvas.
   * Це повністю вирішує проблему відновлення після розриву зв'язку (гравець просто завантажує стан з БД при перезавантаженні).

2. **Realtime Broadcast (Трансляція повідомлень):**
   * Використовується для швидких "тимчасових" даних, які не потрібно зберігати в БД.
   * **Рух мишки (Ховер):** Показує напівпрозору проекцію фігури опонента на полі в реальному часі, коли він вибирає місце для ходу.
   * **Емодзі / Реакції:** Можливість швидко надіслати смайлик опоненті.

3. **Realtime Presence (Відслідковування онлайн-статусу):**
   * Дозволяє бачити, чи опонент онлайн, чи відключився (показувати зелений/червоний індикатор біля його імені).

## 🚀 Пропонований план розробки (Етапи)

### Етап 1: Створення бази даних та API у Supabase
1. Налаштування схеми БД (таблиці `rooms`, `players`, `game_states`).
2. Налаштування політик безпеки (Row Level Security - RLS) або створення PostgreSQL функцій (RPC) для безпечного виконання ходів (перевірка черги ходу, валідація на бекенді тощо).

### Етап 2: Створення UI для лобі та підключення
1. Розробка HTML/CSS для екрану вибору ("Локально" / "Онлайн"), створення кімнати та лобі.
2. Інтеграція Supabase SDK та логіки приєднання/створення кімнати.
3. Реалізація Presence для відображення підключених гравців у реальному часі.

### Етап 3: Створення мережевого ігрового циклу (Game Sync Loop)
1. Реалізація покрокової синхронізації через підписку на `game_states`.
2. Синхронізація дій:
   * Натискання "Roll Dice".
   * Обертання фігури (синхронізується через локальний стан і надсилається при встановленні).
   * Розміщення фігури (перевірка координат, запис у БД, трансляція іншим гравцям).
   * Спеціальні режими дублів (малювання стін, Tectonic Overwrite).
   * Кнопка "Pass".

### Етап 4: Додаткові інтерактивні фічі (Polishing)
1. Трансляція ховеру мишки супротивника (напівпрозорий блок на полі).
2. Чат або система швидких емодзі.
3. Обробка дисконектів та автоматичний таймер ходу (за бажанням).

## 🤝 Прийняті архітектурні рішення (Decisions Made)

1. **Фронтенд-структура:** Використовуємо **Vite + Vanilla JS** з поділом коду на модулі (`audio.js`, `canvas.js`, `db.js`, `game.js`, `ui.js`, `app.js`).
2. **Аутентифікація:** Інтегруємо **Google OAuth** через Supabase. Це дозволить гравцям логінитися в один клік, а також автоматично підтягуватиме їхнє ім'я користувача та аватарку з Google для створення профілю у `profiles`.
3. **Логіка валідації:** Використовуємо **серверну валідацію ходів на рівні бази даних**. Будь-яка дія (кидок кубиків, поворот та розміщення фігури) надсилатиметься у вигляді виклику збереженої процедури PostgreSQL (RPC). БД перевірятиме:
   * Чи зараз хід цього гравця.
   * Чи відповідає розмір фігури випавшим кубикам.
   * Чи не накладається фігура на інші об'єкти.
   * Чи дотримані правила дотику сторін (сусідства клітинок) та правила спеціальних режимів дублів.
   Тільки після успішної перевірки хід записуватиметься в БД, а стан буде оновлюватись для всіх гравців. Це унеможливить читерство та пошкодження стану через баги клієнта.
